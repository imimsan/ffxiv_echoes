Mental model

AoE表示は5段階で決まる

画面に赤い範囲が出るまでに、入力イベント、形状解決、経路選択、描画、破棄の5つの判断があります。 どこか1つがズレると「遅い」「残る」「変な範囲」「重い」になります。

Capture

Cast / ActionEffect / ObjectTable からイベントを作る。PC由来か、対象座標があるかがここで決まる。

Resolve

Lumina Action の EffectRange / CastType / Omen から形状と中心種別を推定する。

Route

ミニマップ、床塗り、オブジェクトAoE、録画予測のどれに流すかを選ぶ。

Render

WorldToScreen でワールド座標を画面に投影し、円・扇・矩形・ドーナツを描く。

Expire

cast完了、cancel、戦闘終了、zone変更、TTLで消す。ここが漏れるとAoEが残る。

Inputs

入力イベントの契約

私の認識では、AoE表示の安全性は「発動元が敵か」「中心座標がどこか」「事前イベントか事後イベントか」に強く依存します。

CastStartedEvent 敵 IBattleNpc の IsCasting をフレーム監視し、初観測または非詠唱から詠唱へ変わった時点。事前警告に使える。 SourceIdCastActionIdCastTimeTargetWorld 初観測時点で既に詠唱中なら本当の開始より遅い。TargetWorld は開始時snapshotなので、動く対象中心AoEは着弾時とずれる。
CastCompletedEvent 詠唱バーが非詠唱に戻り、直前進捗が総詠唱時間に近いときの推定完了。 Impact昇格Fade開始 ダメージ発生フレームそのものではない。完了イベントが拾えない場合、Confirmed が TTL まで残る。

Routes

描画経路は役割が違う

「ミニマップに出る」と「床に出る」は同じ意味ではありません。片方だけ出る、片方だけ遅い、という状態は設計上あり得ます。

AutoTelegraphService

敵キャスト/瞬間アクションをミニマップへ送る経路。

  • show_auto_telegraphs がONのときのみ動く。
  • 全体攻撃マーク済み、友軍、巨大すぎる円はスキップ。
  • ActionUsedEvent は先読みではなく、ノーキャスト/着弾後補完として扱う。
  • 床塗りはここでは描かず、ActorTrackedAoeServiceが担当する。

ActorTrackedAoeService

ワールド座標に床AoEを毎フレーム描く経路。

  • CastStarted で Confirmed、CastCompleted で Impact。
  • 予測AoEは Predicted として先に出る。
  • caster中心は開始時位置を固定し、target中心は TargetWorld → TargetId → actor位置の順で解決。

AddObjectAoeService

パラデイグマ系の出現オブジェクトAoEを描く経路。

  • 保存済み rule → cache → dictionary → recording_action → recording の順で解決。
  • 同名候補が多すぎる live group は描かない。
  • 発動元actor名の recording_action 誤学習は無視。

PredictedCastReminder

録画集計から未来のキャストを予測して先出しする経路。

  • CastStarted が来れば Confirmed へ置き換わる。
  • 来なければ予測着弾後およそ1秒で自動消滅する想定。
  • 分岐や同期オフセットの精度が表示時刻に影響する。
Geometry

Lumina CastType の解釈

自動AoEの中心は、CastType によって caster中心か target/ground中心かが変わります。 ここを間違えると「範囲は出るが場所が違う」になります。

CastType 2: target centered circle 対象/地面中心の円。TargetWorld があれば最優先。Hitbox は加算しない。
判定 現在の認識 自動描画しない条件
EffectRange 0 < range <= 50m を信頼。50m超は特殊/全体/誤データ扱い。 range 0 以下、50m超、またはアリーナ半径の1.5倍級の円。
Omen 床塗りの donut 判定は CastType 6/7/10 または Omen 53/60-64 を優先。ミニマップ用 gimmick 推定では Omen 1-5 / 10-14 / 40-42 も補助情報として使う。 未知 Omen は CastType fallback。未知 CastType は「適当な円」へ落とさず描かない。
Hitbox CastType 3/4/5 は caster hitbox を EffectRange に加算。 target/ground中心の 2/12/13 には加算しない。
Rotation Cone / Rect / Cross はキャスト開始時の rotation snapshot を基本にし、描画角は π/2 - rotation へ変換。 rotation が取れない特殊ケースは向き指定ルールか手動 AoE Zone へ寄せる。
Object AoE

パラデイグマ系の認識

オブジェクトAoEは、敵キャストのAoEとは別物です。発動元はボスでも、実際の危険範囲は出現オブジェクトの位置に紐づきます。

優先順位

私の認識では、object AoE はまず保存済み object_aoe_rules を見ます。 その後、同一戦闘内cache、dictionary、録画済み action、object出現後の録画学習の順で形状を解決します。

  • manual/user-authored rule は明示指定なので強い。
  • dictionary / recording_action / recording 由来は学習後に object_aoe_rules へ保存され、次回は最優先になる。
  • 同名オブジェクトは DataId が揺れる可能性があるため名前優先。

今回の重要な仮説

ゾディアーク のような既知の発動元actorが recording_action の object rule として保存されている場合、 それはオブジェクトAoEではなく誤学習として扱うべきです。

  • 保存済み誤ルールは削除せず、実行時に無視する。
  • 新規保存時も同条件なら保存しない。
  • ケツァクウァトル / ケツァクワァトル は同一候補として扱う。

ミニマップと床塗り

object AoE は arena_view の AoeZones としてミニマップへ渡されます。 AoeZones がある場合、旧 gimmick 近似は抑制し、ユーザー/学習済み zone を正として描画します。

  • live_floor_paint=false なら床塗りせず、ミニマップだけ表示できる。
  • suppress_auto_aoe=true なら同一 cast の Lumina 自動ミニマップAoEを消す。

group anchor

matched_object は代表位置、each_matched_object は group 内の全位置へ展開されます。 パラデイグマのような複数出現では、ここで「1個だけ出る」か「全個体に出る」かが決まります。

  • ObjectGroupAppearedEvent は派生イベントなので、録画には直接残らない。
  • 名前一致は exact / startswith / 既定 contains。
object_appear出現イベントが来るなら、位置が明確なので最も早く描ける。
live scanappear が来ない既存ObjectTable上のギミックを拾う救済。
max 8同名候補が9以上ならボスパーツ/背景ノイズの可能性が高い。
dedup同じ object AoE は表示時間中に再発火しない。
Lifecycle

床AoEの表示寿命

床塗りは「ただ出して消す」ではなく、段階ごとに濃さと意味が違います。 ここをユーザー期待と合わせないと、早すぎる/遅すぎる/残りすぎる印象になります。

Predicted

録画予測由来。着弾時刻が近づくほど濃くなる。CastStarted が来れば Confirmed に置換。期限は予測着弾 + 1.0秒。

Confirmed

実キャスト開始。キャスト中の確定予告として表示。寿命は原則 CastTime + 3.0秒で、同じ source/cast の Predicted を置換。

Impact

CastCompleted または instant action。着弾済みフィードバックとして 0.3秒だけ強調赤で見せる。

Fade

余韻。1.5秒で透明化し、期限切れで active list から消える。

Performance

重くしないための描画境界

AoE表示時の重さは、形状数、半径、WorldToScreen回数、投影失敗時の描き直しで増えます。 仕様として「描かない判断」を持たせることが、正確さと同じくらい重要です。

現在入っている抑制

  • 中心距離 - 半径 が 60m を超える床AoEは投影前にskip。
  • 円/扇のsegmentsは半径に応じて増やすが 24-64 にclamp。
  • 円/扇の頂点配列は ArrayPool を使って確保圧を下げる。
  • live drawer が空になれば WorldOverlayWindow を閉じる。

安全側の描画失敗

投影に失敗した点を含む円/扇/中心矩形は、非凸ポリゴン事故を避けるため丸ごと描かない。 Rect は中心線 fallback を持つため、情報量を落としてでも破綻しにくくする。

  • 巨大AoEは「全部描く」よりも raid-wide / 明示定義へ寄せる。
  • object group が多すぎる場合は、背景・ボスパーツの誤検出として止める。
負荷源 設計上の境界 レビューしたい点
同時表示数 object AoE は同名候補数・重複発火・表示時間で抑える。 パラデイグマで必要な最大同時数を明文化したい。
巨大円/大扇 50m超 EffectRange、arena半径1.5倍級の円、60m外の床AoEは描かない。 raid-wide でも手動 user layout だけは残す例外を維持するか。
短命object 出現時に rule を温め、live_floor_paint で床塗り有無を分ける。 着弾同時表示に落ちているケースは object_appear / live scan の不足を疑う。
Failure modes

ズレやすい点と現在の見立て

ここは特にレビューしてほしいところです。私の認識が間違っていれば、次の修正方針も間違います。

意味不明な巨大AoEが出る

原因候補: ボス本体/ボスパーツが object AoE rule に誤学習される、または live scan が同名候補を拾いすぎる。

パラデイグマのAoEが遅い

原因候補: object_appear が来ず、ActionUsedEvent の Impact まで待っている。期待は object位置確定時点での先出し。

AoE表示時に重い

原因候補: 同時に多数の大円/扇/矩形を描き、WorldToScreen 呼び出しが増える。segments上限、距離カリング、object group上限で抑える。

AoEが残り続ける

原因候補: CastCompleted/Cancel/CombatEnded/ZoneChanged のどこかで active state が掃除されない、または TTL が長すぎる。

Review

確認したい仕様判断

実装修正に戻る前に、以下の認識が合っているかを確認したいです。 特に「出すべきでないAoE」と「遅くても許されないAoE」を分けるのが重要です。

1. パラデイグマ系は「objectが見えた瞬間」に床AoEを出すべきか

私の認識では YES。ActionUsedEvent まで待つのは遅すぎるため、object_appear/live scan/object rule を優先するべきです。

2. ボス本体名の recording_action object rule は常に誤学習扱いでよいか

私の認識では YES。ただし手動で明示した manual rule は例外として残します。

3. Luminaだけで不明なAoEは適当な円を出さない方針でよいか

私の認識では YES。不明な10m円は誤誘導になりやすく、手動 mechanic / AoE Zone に寄せるべきです。

4. 画面床塗りとミニマップは同時に出るべきか

私の認識では原則 YES。ただし floor paint のON/OFFと minimap のON/OFFは独立設定として扱うべきです。

5. ActionUsedEvent は「予告」ではなく「着弾/補完」扱いでよいか

私の認識では YES。ノーキャスト技の補完には使えますが、パラデイグマの先出しには遅すぎます。
